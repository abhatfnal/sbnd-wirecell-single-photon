## 2. The shower direction and end point: what the stored quantities really are (the open question of Phase 10, resolved)

* **Start point.** `Shower::calculate_kinematics` (`PRShower.cxx`): for a start connection type 1 (or no fit point cloud) the start point is the **end of the start segment's fit that touches the vertex** (`fits.front()` if `dirsign == +1`, else `fits.back()`); for connection type 2/3 the start point is derived from the anchor vertex / closest point (`shower_clustering` sets it from the nearest vertex). It is **not** a point chosen from the charge centre.
* **End point.** `get_end_point()` is **not a point on the shower's charge**: for a single-segment shower it is the opposite end of the start segment (`fits.back()`/`front()` by `dirsign`); for a multi-segment shower it is the **farthest *vertex* of the shower's trajectory view from the start point** (`PRShower.cxx`, the "farthest vertex" loop; the source itself documents that the view's vertex set can include vertices no member segment touches, with `endpoint_skip_orphan_vertices` as the guard).
* **The `T_pf` node of a shower** (`fill_bee_pf_tree`, `MultiAlgBlobClustering.cxx`) is written with `data.start = shower->get_start_point()` and `data.end = shower->get_end_point()` in cm; pseudo photon nodes (the invisible photon between the vertex and a displaced shower) have `start == end` at the shower start. So the **`T_pf` chord (end - start) is the line from the shower start to the farthest trajectory vertex**: a whole-shower axis, usually 50-150 cm long.
* **The direction the tagger itself uses** is different: `shower_cal_dir_3vector(shower, vertex_point, 15 cm)` (25 cm for high energies / drift-parallel showers; the start segment's own direction for a start segment > 12 cm): the unit vector from the point `vertex_point` (the end of the start segment nearest the vertex) to the **mean of all the shower's fit points within the cut distance**. Only its angle to the beam (+z) is stored: `shw_sp_angle_beam` [deg]; **no vector is stored in the CAF**.
* **MEASURED (1,151 selected showers whose row is found):** the `T_pf` start point equals the tagger's start point (for the detached showers `|d(T_pf start, vertex) - shw_sp_shw_vtx_dis|` has median 3e-7 cm, correlation 1.000; for attached showers the start is at the vertex, 0.3 % exceed 3 cm), so **the chord start is in the SCE-corrected frame of the vertex**. The chord direction agrees with the true photon direction with median cos 0.984 (median angle 10.2 deg, 68 % within 15.8 deg, 82.9 % with cos > 0.9, 3.0 % negative; 5.3 % negative for truth-0p, 0.8 % for truth-1p); a reco-only alternative (vertex -> shower start, defined for detached showers) has median cos 0.9996 for the 567 detached showers (97.0 % > 0.9) because for a detached shower with an anchored vertex that line follows the photon path; the `shw_sp_angle_beam` residual against the true beam angle has median +0.65 deg and 68 % half-width 5.6 deg (10 % beyond 3 half-widths). All of these are in `tables/common_observables/photon_direction_resolution.csv`.
* **Convention used by this phase (decided here, documented, not changed afterwards):** the photon direction of the Delta mass is the **`T_pf` chord** (the only direction stored as a vector); the vertex -> start direction is carried as a reco-only alternative and its effect is quantified (`delta_mass_substitution_study.csv`). Directions are **never flipped using truth**.

## 3. Positions and frames

`kine_nu_*_corr`, the `T_pf` start points and `shw_sp_shw_vtx_dis` all use the SCE-corrected frame (the tagger's `sp_corr`; identity when the correction is off). MEASURED consistency: `T_tagger.nu_{x,y,z}` equals `kine_nu_*_corr` exactly; the `T_pf` start reproduces `shw_vtx_dis` to 3e-7 cm. The true vertex of the truth tables is not SCE-distorted (Phase 9 compared the two directly).

## 4. The proton direction

The `T_pf` node of a track row has `start`/`end` = the segment's end points in the order the pattern recognition assigned (`dirsign`-dependent); the orientation rule of track nodes was **not read** in the source. MEASURED (545 truth-correct selected proton rows): the chord start is the endpoint nearer to the reco vertex in 99.8 % of the cases, cos with the true proton direction has median 0.998, 93.4 % above 0.9, **4.95 % negative; the negative cases are concentrated at very short chords** (28 % negative below 3 cm, 5.5 % at 3-6 cm, 0 % above 40 cm) **and in shower-typed proton rows** (44 % negative vs 1.8 % for track rows). Re-orienting the chord away from the reco vertex (a reco-only rule) changes nothing (4.8 % negative): the pathology is a direction that is undefined for a very short object, not a sign convention. No flipping is applied.

## 5. Energy of the selected shower

`shw_sp_energy` is the energy of a **shower object** (`kine_best`): MEASURED 99.9 % of the selected showers have `kine_energy_info == 2` (charge-based). It is the energy of the shower, not of the photon: for a photon that is split over several objects the counted object is a fragment (Phase 9); for the truth-correct selected photons (1,148) the median E_reco/E_true is 1.03 with 68 % half-width 12.7 % (`photon_energy_response.csv`).

## 6. Not used / caveats

* `shw_sp_*` fields are the **frozen BDT inputs** and are filled only for the max shower: a candidate without a max shower has `shw_sp_filled = 0` and all the struct defaults; these defaults are not physical values.
* The MIP dQ/dx normalisation value (`m_mip_dqdx_median`, `~43000 e/cm` in the code comment) and the choice between the recombination-model and the legacy dE/dx path are production-configuration values that were **not read**; MEASURED consistency: the peak of the nueCC primary-electron `shw_sp_vec_median_dedx` is at 2.1 MeV/cm, i.e. the MIP dE/dx of the SBND field (question to the production authors in `QUESTIONS_FOR_HAIWANG_HANYU.md`).
* `kine_reco_Enu` is a **visible-energy sum**, not a neutrino-energy estimate: for NC the outgoing neutrino carries away energy (MEASURED: median `kine_reco_Enu` / true E_nu = 0.48 but / true visible energy (photon + primary protons) = 1.05, `reco_enu_response.csv`).
